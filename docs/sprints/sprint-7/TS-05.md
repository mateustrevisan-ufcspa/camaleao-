# TS-05 · Supabase CLI 3.x no projeto (1 SP)

> Como equipe, queremos usar o Supabase CLI 3.x com a versão fixada no projeto, para que nenhum comando pare no `[inbucket]` do `config.toml` e para que todo comando contra o banco de produção peça confirmação antes de mudar alguma coisa.

**Tipo:** technical story · **Implementa:** Laís · **Revisa:** Alissa · **Branch:** `ts-05-supabase-cli-3` · **Depende de:** nada · **PR pronto:** segunda 09/11, 14h (a TS-04 parte dela) · **Merge:** segunda 09/11, logo depois da aprovação, o primeiro da sprint (todas trazem a `main` depois)

## Critérios de aceitação

- [ ] `supabase/config.toml` com `[local_smtp]` no lugar de `[inbucket]`, com as mesmas chaves
- [ ] O CLI fixado em `supabase@3.0.0` nos scripts do `package.json` e no `scripts/env-local.mjs`; nenhum arquivo em uso chama o CLI sem versão
- [ ] `npm run db:reset`, `npm run env:local`, lint, build, testes de fumaça e de acesso verdes no local e na esteira
- [ ] `docs/processo/banco-de-producao.md` com os comandos da versão 3 (`--remote` e a confirmação antes do `db push`), conferidos com um `migration list --remote` no `camaleao-producao`, sem aplicar nada
- [ ] Registro no `PROGRESSO.md` da versão antiga e da nova, com o que mudou para quem faz `db push`

## Por que agora

- Em 04/11, um `npx supabase` sem versão baixou a 3.0.0, que parou no `[inbucket]` do `config.toml` (registro da Sprint 6). Desde 02/11 a 3.0.0 é a versão padrão do npm, então qualquer pessoa que esquecer a versão cai no mesmo erro.
- A versão 3 é "local por padrão": `db push`, `migration list` e `db dump` só vão ao banco hospedado com `--remote`, e todo comando que muda o banco hospedado pergunta antes, com "não" como resposta padrão. Nesta sprint a Alissa e a Laís passam a fazer `db push` (ação da retrospectiva), então essa trava vale mais do que antes.
- A versão 2.108.0 e as seguintes já leem `[local_smtp]`. Dá para trocar o `config.toml` primeiro e conferir com a 2.119.0, e só depois trocar a versão.

## O que muda nos comandos

| Para quê | Até hoje (2.119.0) | Depois desta story (3.0.0) |
| --- | --- | --- |
| Subir o banco local | `npm run db:start` | igual (o script muda por dentro) |
| Recriar o banco local | `npm run db:reset` | igual |
| Ver o que está aplicado em produção | `npx --yes supabase@2.119.0 migration list` (com o projeto ligado) | `npx --yes supabase@3.0.0 migration list --remote` |
| Aplicar migração em produção | `npx --yes supabase@2.119.0 db push` | `npx --yes supabase@3.0.0 db push --remote` e responder `y` na pergunta |
| `--include-all` (migração de nome anterior) | `db push --include-all` | `db push --include-all --remote` |
| Ligar o CLI ao projeto | `npx --yes supabase@2.119.0 link --project-ref ...` | `npx --yes supabase@3.0.0 link --project-ref ...` |

**Atenção:** na 3.0.0, `db push` **sem** `--remote` aplica no banco local, e não em produção. Quem esquecer o `--remote` não estraga nada, mas também não publica: por isso o `migration list --remote` antes e depois continua obrigatório.

A versão 3 também lê os arquivos `.env*` da pasta `supabase/` e da raiz, e variáveis `SUPABASE_*` passam por cima do `config.toml`. O nosso `.env.local` só tem variáveis `NEXT_PUBLIC_*`, então nada muda. **Regra a partir de agora:** variável nova do sistema não começa com `SUPABASE_` (a US-24a usa `CHAVE_SECRETA_DO_SUPABASE` por isso).

## 4. `scripts/env-local.mjs`

A versão muda, e a leitura do `status` fica tolerante: a 3.0.0 acrescentou um objeto `target` nas respostas em JSON, e o nome das chaves pode ter mudado. Rode antes, para ver a saída real:

```bash
npm run db:start
npx --yes supabase@3.0.0 status -o json
```

Anote no PR quais são as chaves da URL da API e da chave anônima (ou publicável). Depois troque o trecho do `status`:

```diff
 let status
 try {
-  status = JSON.parse(execSync('npx --yes supabase@2.119.0 status -o json', { encoding: 'utf8', stdio: ['ignore', 'pipe', 'ignore'] }))
+  status = JSON.parse(execSync('npx --yes supabase@3.0.0 status -o json', { encoding: 'utf8', stdio: ['ignore', 'pipe', 'ignore'] }))
 } catch {
   console.error('Supabase local não está rodando. Rode `npm run db:start` primeiro.')
   process.exit(1)
 }
 
+// A 3.0.0 pode trazer os valores dentro de outro objeto e com outro nome.
+// Procura nos dois níveis, pelos nomes conhecidos.
+function valor(...nomes) {
+  for (const fonte of [status, status.stack, status.local, status.data]) {
+    if (!fonte || typeof fonte !== 'object') continue
+    for (const nome of nomes) if (typeof fonte[nome] === 'string' && fonte[nome] !== '') return fonte[nome]
+  }
+  console.error(`O status do Supabase não trouxe ${nomes[0]}. Rode npx --yes supabase@3.0.0 status -o json e ajuste este script.`)
+  process.exit(1)
+}
+
 writeFileSync(
   '.env.local',
   [
     '# Gerado por scripts/env-local.mjs: Supabase local, sem dado real.',
-    `NEXT_PUBLIC_SUPABASE_URL=${status.API_URL}`,
-    `NEXT_PUBLIC_SUPABASE_ANON_KEY=${status.ANON_KEY}`,
+    `NEXT_PUBLIC_SUPABASE_URL=${valor('API_URL', 'api_url', 'apiUrl')}`,
+    `NEXT_PUBLIC_SUPABASE_ANON_KEY=${valor('ANON_KEY', 'PUBLISHABLE_KEY', 'anon_key', 'publishable_key')}`,
     '',
   ].join('\n'),
 )
-console.log(`.env.local criado para ${status.API_URL}`)
+console.log('.env.local criado para o Supabase local')
```

Se a saída da 3.0.0 usar outros nomes, acrescente-os na chamada de `valor` e escreva no PR quais eram.

````markdown

```bash

````
