# US-07 · Contato e consentimento de mensagens (5 SP)

> Como apoiadora do Instituto, eu quero autorizar ou recusar o recebimento de mensagens do Instituto, para que meus dados sejam usados apenas como eu permiti.

**Tipo:** user story · **Implementa:** Bibiana · **Revisa:** Mateus · **Branch:** `us-07-consentimento-de-mensagens` · **Depende de:** nada para começar. Os testes da Parte E usam a pasta `tests/acesso`, que chega à `main` com a SEC-03 (PR #11).

## Critérios de aceitação

- [ ] Deve permitir registrar telefone, e-mail e aniversário na ficha
- [ ] Deve registrar a autorização com data e versão do termo
- [ ] Deve impedir envio de mensagem a quem não autorizou
- [ ] Deve oferecer caminho de descadastro a qualquer momento

## O problema

A ficha já guarda telefone, e-mail e aniversário, e as telas de cadastro e edição já têm os três campos. O que não existe é a resposta para a pergunta "esta pessoa deixou o Instituto falar com ela?". Sem essa resposta, o agradecimento automático (US-21) e os aniversariantes (US-22), que vêm mais adiante, não teriam de onde tirar a lista de quem pode receber mensagem.

## Decisões

- **O primeiro critério já é atendido pelo sistema.** O que esta story acrescenta é a prova: um teste que cadastra os três dados e confere que aparecem na ficha. Diga isso com todas as letras no Pull Request.
- **A autorização é um histórico, não uma caixinha marcada.** Cada decisão da pessoa vira uma linha nova na tabela `message_consents`: autorizou ou retirou, quando, com qual versão do termo e quem registrou. A situação atual é a linha mais recente. Ninguém altera nem apaga linha, nem a coordenação. É esse histórico que comprova o consentimento se alguém perguntar.
- **Data e autoria são do servidor.** Quem registra não escolhe a data nem em nome de quem o registro fica. Um gatilho no banco preenche as duas coisas.
- **Três situações, e não duas:** autorizou, retirou, e ainda não foi perguntada. Quem nunca foi perguntada não recebe mensagem. Deixar a caixa desmarcada no cadastro não vira "recusou".
- **O termo tem versão.** O texto lido para a pessoa fica em `lib/termo-mensagens.ts`, com uma versão. Mudou o texto, muda a versão, e as autorizações antigas continuam apontando para o texto que a pessoa ouviu.
- **"Impedir envio" sem existir envio.** O sistema ainda não manda mensagem. O critério é atendido criando a única porta por onde um envio futuro pode passar: a view `message_recipients`, que só traz quem autorizou e não retirou. A regra fica escrita no documento da Parte B, e um teste prova que quem não autorizou, ou retirou, não aparece nela. É o mesmo raciocínio que a US-23 usou para mesclagem e cancelamento.
- **Descadastro é um botão na ficha.** A pessoa pede no balcão ou pelos canais do Instituto, e qualquer integrante da equipe registra a retirada, que vale na hora. Quando existir mensagem de verdade, ela precisa trazer também um caminho que a própria pessoa use sozinha. Fica anotado para a US-21.
- **O texto do termo é uma proposta.** Quem aprova a redação é o Instituto. O Mateus envia o texto à Flávia; até a resposta, vale a versão `2026-10`. Se ela pedir mudança, entra uma versão nova.

## Parte A · Banco

### A1. Migração nova

Arquivo novo: `supabase/migrations/20261013090000_consentimento_de_mensagens.sql`.

```sql
-- US-07 · Contato e consentimento de mensagens
-- Registro de quem autorizou, ou deixou de autorizar, mensagens do Instituto.
-- Texto e versões do termo: docs/privacidade/termo-de-mensagens.md

-- ─────────────────────────────────────────
-- 1. Registro de autorização. Só cresce: cada linha é uma decisão da pessoa
--    (autorizou ou retirou), com data, versão do termo e quem registrou.
--    A situação atual é sempre a linha mais recente. Ninguém altera nem apaga
--    uma linha, nem a coordenação: é o histórico que comprova o consentimento.
-- ─────────────────────────────────────────

create table public.message_consents (
  id           uuid primary key default gen_random_uuid(),
  client_id    uuid not null references public.clients(id) on delete cascade,
  authorized   boolean not null,
  term_version text not null check (btrim(term_version) <> ''),
  recorded_at  timestamptz not null default now(),
  recorded_by  uuid references public.users(id) on delete set null
);

create index idx_message_consents_client on public.message_consents (client_id, recorded_at desc);

-- Data e autoria são do servidor: quem registra não escolhe nenhuma das duas.
create or replace function public.message_consents_carimbo()
returns trigger
language plpgsql
set search_path = ''
as $$
begin
  new.recorded_at := clock_timestamp();
  new.recorded_by := auth.uid();
  return new;
end;
$$;

create trigger message_consents_carimbo
  before insert on public.message_consents
  for each row execute function public.message_consents_carimbo();

alter table public.message_consents enable row level security;

create policy "equipe le" on public.message_consents
  for select to authenticated using (public.eh_equipe());
create policy "equipe registra" on public.message_consents
  for insert to authenticated with check (public.eh_equipe());
-- Sem política de update nem de delete: ninguém altera nem apaga pela API.
revoke all on public.message_consents from anon;
revoke update, delete, truncate on public.message_consents from authenticated;

-- ─────────────────────────────────────────
-- 2. Situação atual de cada pessoa: a decisão mais recente.
--    Quem nunca foi perguntada não aparece aqui, e não aparecer conta como
--    "não autorizou".
-- ─────────────────────────────────────────

create view public.message_consent_status
with (security_invoker = true) as
select distinct on (mc.client_id)
  mc.client_id,
  mc.authorized,
  mc.term_version,
  mc.recorded_at
from public.message_consents mc
order by mc.client_id, mc.recorded_at desc, mc.id desc;

revoke all on public.message_consent_status from anon;
grant select on public.message_consent_status to authenticated;

-- ─────────────────────────────────────────
-- 3. A trava do envio. Toda funcionalidade que mandar mensagem (agradecimento,
--    aniversário, campanha) monta a lista de destinatários a partir desta view,
--    e de nenhum outro lugar. Quem não autorizou, ou retirou a autorização, não
--    está nela.
-- ─────────────────────────────────────────

create view public.message_recipients
with (security_invoker = true) as
select
  c.id   as client_id,
  c.name,
  st.term_version,
  st.recorded_at as authorized_at
from public.clients c
join public.message_consent_status st on st.client_id = c.id
where st.authorized is true;

revoke all on public.message_recipients from anon;
grant select on public.message_recipients to authenticated;

-- Para conferir uma pessoa só, na hora de enviar.
create or replace function public.pode_receber_mensagem(p_client_id uuid)
returns boolean
language sql
stable
set search_path = ''
as $$
  select coalesce(
    (select st.authorized from public.message_consent_status st where st.client_id = p_client_id),
    false
  )
$$;
```

### B2. `docs/privacidade/termo-de-mensagens.md`

Arquivo novo, escrito por você (a pasta `docs/privacidade/` pode ainda não existir; a SEC-05 também cria um arquivo nela). Estrutura sugerida:

1. **O que é.** Uma frase: o registro de quem autorizou o Instituto a enviar mensagens, e a regra de que só essas pessoas recebem.
2. **O termo.** O texto da versão `2026-10`, igual ao de `lib/termo-mensagens.ts`, e uma tabela de versões (versão, data, o que mudou, quem aprovou no Instituto). A primeira linha fica com "aprovação do Instituto: pendente, texto enviado em DD/10".
3. **Como a autorização é registrada.** No cadastro (caixa de seleção) e na ficha (botão). Cada registro guarda a decisão, a data, a versão do termo e quem registrou. Nada é alterado nem apagado.
4. **As três situações.** Autorizou, retirou, ainda não foi perguntada. Só a primeira recebe mensagem.
5. **Regra de envio.** Toda funcionalidade que enviar mensagem monta a lista a partir da view `message_recipients` e de nenhum outro lugar. Vale para a US-21 (agradecimento) e para a US-22 (aniversariantes). Pull Request que busque telefone ou e-mail para envio fora dessa view não é aprovado.
6. **Descadastro.** Como a pessoa pede (no balcão ou pelos canais do Instituto), quem registra (qualquer integrante da equipe, na ficha), e que vale na hora. Anote o ponto em aberto: a mensagem enviada pela US-21 precisa trazer um caminho que a própria pessoa use sem depender da equipe.
7. **O que acontece se a ficha for apagada.** O histórico de autorização vai junto.

import { TERMO_MENSAGENS } from '@/lib/termo-mensagens'
import type { MessageConsent } from '@/types'

export async function fetchMessageConsent(clientId: string): Promise<MessageConsent | null> {
  return getMessageConsent(clientId)
}

// Autorizar grava a versão do termo que está valendo agora.
export async function authorizeMessages(clientId: string): Promise<MessageConsent | null> {
  await addMessageConsent(clientId, true, TERMO_MENSAGENS.versao)
  return getMessageConsent(clientId)
}

// Retirar a autorização (descadastro) vale na hora e não depende de motivo.
export async function revokeMessages(clientId: string): Promise<MessageConsent | null> {
  await addMessageConsent(clientId, false, TERMO_MENSAGENS.versao)
  return getMessageConsent(clientId)
}

// Apoio dos testes de acesso: login pela API com a chave anônima, nunca com a
// chave de serviço (que ignora todas as políticas e faria qualquer teste passar).
import { createClient, type SupabaseClient } from '@supabase/supabase-js'
import { USUARIA } from '../fumaca/apoio'

const URL_API = process.env.NEXT_PUBLIC_SUPABASE_URL as string
const CHAVE_ANONIMA = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY as string

export const COORDENACAO = USUARIA.email
export const CAIXA = 'caixa@camaleao.local'

export async function entrarNaApi(email: string): Promise<{ api: SupabaseClient; id: string }> {
  if (!URL_API || !CHAVE_ANONIMA) {
    throw new Error('Faltam as variáveis do Supabase local. Rode npm run env:local com o banco ligado.')
  }
  if (!/127\.0\.0\.1|localhost/.test(URL_API)) {
    throw new Error(`Os testes de acesso só rodam no banco local, e o endereço configurado é ${URL_API}.`)
  }
  const api = createClient(URL_API, CHAVE_ANONIMA, { auth: { persistSession: false } })
  const { data, error } = await api.auth.signInWithPassword({ email, password: USUARIA.senha })
  if (error || !data.user) {
    throw new Error(`Login na API falhou para ${email}: ${error?.message}`)
  }
  return { api, id: data.user.id }
}

// Com as políticas, uma leitura proibida costuma voltar vazia em vez de dar erro.

  r.error !== null || (Array.isArray(r.data) && r.data.length === 0)

// Confere, pela API e como caixa, o registro de autorização e a trava do envio.
import { test, expect } from '@playwright/test'
import type { SupabaseClient } from '@supabase/supabase-js'
import { CAIXA, COORDENACAO, entrarNaApi } from './apoio'

const MARCA = 'TESTE US-07'
const TERMO = 'teste-1'

let coordenacao: SupabaseClient
let coordenacaoId: string
let caixa: SupabaseClient
let caixaId: string
let pessoaId: string

const destinatarios = () => caixa.from('message_recipients').select('client_id').eq('client_id', pessoaId)

test.beforeAll(async () => {
  ;({ api: coordenacao, id: coordenacaoId } = await entrarNaApi(COORDENACAO))
  ;({ api: caixa, id: caixaId } = await entrarNaApi(CAIXA))

  // Apagar a pessoa apaga junto o histórico de autorização dela.

// Os testes abaixo contam uma história só, nesta ordem.
test.describe.configure({ mode: 'serial' })

test('quem nunca foi perguntada não recebe mensagem', async () => {

  // A caixa tenta escolher a data e pôr o registro no nome de outra pessoa.
  const registro = await caixa
    .from('message_consents')
    .insert({ client_id: pessoaId, authorized: true, term_version: TERMO, recorded_at: '2020-01-01T00:00:00Z', recorded_by: coordenacaoId })
    .select('authorized, term_version, recorded_at, recorded_by')
    .single()
  expect(registro.error).toBeNull()
  expect(registro.data?.term_version).toBe(TERMO)
  expect(registro.data?.recorded_by).toBe(caixaId)
  expect(Date.now() - new Date(registro.data!.recorded_at).getTime()).toBeLessThan(60_000)

  expect((await destinatarios()).data).toHaveLength(1)
})

test('o registro não pode ser alterado nem apagado', async () => {
  const alterar = await caixa.from('message_consents').update({ authorized: false }).eq('client_id', pessoaId).select()

  expect((await destinatarios()).data).toHaveLength(1)
})
