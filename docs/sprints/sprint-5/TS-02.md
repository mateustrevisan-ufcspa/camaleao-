# TS-02 · Banco de produção novo, montado só pelas migrações (5 SP)

> Como integrante da equipe, eu quero um banco de produção montado só pelas migrações do repositório, separado do banco em que a equipe e as avaliadoras testam, para que o Instituto comece a usar o sistema com dados reais sem herdar dados de teste nem migrações aplicadas à mão.

**Tipo:** technical story · **Implementa:** Mateus · **Revisa:** Laís · **Branch:** `ts-02-banco-de-producao` · **Depende de:** nada · **Publica:** o PR só tem documentação; quinta 29/10, depois das 22h

## Critérios de aceitação

- [ ] Deve conferir a diferença entre as migrações do repositório e o banco publicado, transformando em migração o que faltar
- [ ] Deve montar o projeto novo do Supabase só com `supabase db push`, com todas as migrações registradas (`migration list` sem pendência)
- [ ] Deve ter no banco novo os dados de referência das migrações e nenhum dado de teste ou de demonstração
- [ ] Deve ter o roteiro da virada (contas, Auth, variáveis da Vercel, conferência e volta) escrito e ensaiado com um deploy de preview apontando para o banco novo
- [ ] Deve registrar a regra: migração em produção só por `supabase db push`, nunca pelo SQL Editor

**Fora desta story:** a virada em si (trocar as variáveis de produção na Vercel). Ela muda o sistema que as avaliadoras estão usando, então a data sai da revisão com o Instituto em 30/10.

## Por que agora

- **O banco publicado tem só dados de teste,** e as avaliadoras estão lançando mais dados inventados nesta semana. O Instituto não deve começar o uso real em cima disso.
- **As migrações em produção não deixam rastro.** Elas entram pelo SQL Editor, e o projeto hospedado não tem a tabela `supabase_migrations.schema_migrations`. Na Sprint 4, a única forma de saber o que estava aplicado foi conferir objeto por objeto, e a função da US-05 apareceu aplicada sem ninguém saber por quem.
- **A importação das planilhas reais (US-09)** ficou combinada para depois da separação do banco de produção (reunião de 23/10).

## A decisão: o banco novo vira a produção

O banco atual vira o banco de teste (dos deploys de preview e de quem quiser um banco hospedado), e o projeto novo vira a produção. Motivos:

- O banco atual só tem dado de teste, então não há nada a migrar de um para o outro.
- Montar o banco novo só com `db push` prova que as migrações do repositório reconstroem o sistema do zero, e já deixa cada migração registrada.
- O banco atual continua intacto depois da virada, o que faz da volta uma troca de variáveis.

O custo é refazer no projeto novo o que não está nas migrações: contas do Auth e as configurações do Auth.

## Regras para esta semana

- **O banco publicado só é lido.** Nada de `db push`, `db reset` ou SQL de alteração nele nesta story.
- **Nunca rode `db push` com o CLI ligado (`link`) ao banco atual.** Ele não tem a tabela de migrações, então o CLI tentaria aplicar todas desde a primeira. Antes de qualquer `db push`, confira o projeto ligado (passo 4).
- **Nenhuma chave ou senha** em arquivo versionado, no `PROGRESSO.md` ou no Trello. A senha do banco novo fica no gerenciador de senhas da equipe.

## 2. Diferença entre as migrações e o banco publicado (terça 27/10)

Precisa do Docker aberto (o CLI sobe um banco de sombra com as migrações para comparar).

```bash
npx --yes supabase@2.119.0 login
npx --yes supabase@2.119.0 link --project-ref <ref-do-banco-atual>
npx --yes supabase@2.119.0 db diff --linked --schema public,extensions > /tmp/diferenca-producao.sql
```

O `ref` é o código do projeto no endereço do painel do Supabase (`supabase.com/dashboard/project/<ref>`). O `link` pede a senha do banco.

O arquivo `/tmp/diferenca-producao.sql` (fora do repositório) é o SQL que faltaria nas migrações para chegar ao que está publicado. Leia com a Laís:

- **Vazio:** as migrações reconstroem a produção. Anote no `PROGRESSO.md` e siga.
- **Com diferença que faz parte do sistema** (função, política, índice ou coluna criados à mão): vira uma migração nova, `supabase/migrations/20261027090000_acerto_com_producao.sql`, com o trecho e um comentário dizendo de onde veio. Nunca edite migração antiga.
- **Com diferença que é resto** (objeto de teste, cópia de segurança): não vai para a migração. Anote no `PROGRESSO.md` o que foi deixado de fora e por quê.
- **Diferença só de permissão padrão** (`grant` e `alter default privileges` que o Supabase cria sozinho): anote e não transforme em migração, a menos que a Laís ache que muda acesso.

Se o `db diff` reclamar do banco de sombra ou da versão, anote o erro no `PROGRESSO.md` e tente `npx --yes supabase@2.119.0 db pull` numa pasta temporária, comparando o arquivo gerado com as migrações. É a parte da story em que alguém vai precisar pesquisar; reserve a terça para ela.

## 4. Migrações no projeto novo

```bash
npx --yes supabase@2.119.0 link --project-ref <ref-do-projeto-novo>
cat supabase/.temp/project-ref          # tem de mostrar o ref do projeto NOVO
npx --yes supabase@2.119.0 db push --dry-run
```

O `--dry-run` lista as migrações que vão entrar, sem aplicar. Confira que são todas as de `supabase/migrations/` (12 até a `20261022090000_doacao_de_campanha`, mais a de acerto do passo 2, se houver). Então:

```bash
npx --yes supabase@2.119.0 db push
npx --yes supabase@2.119.0 migration list
```

O `migration list` tem de mostrar cada migração nas colunas Local e Remote. Copie a saída para o `PROGRESSO.md` (ela não tem segredo).

**Sem seed.** O `supabase/seed.sql` cria as contas de teste do banco local e o `seed-demo.sql` cria dados de demonstração; nenhum dos dois vai para o projeto novo. Os dados de referência (formas de pagamento, bancos, origens, categorias de item) vêm das próprias migrações.

Conferência no SQL Editor do projeto novo (só leitura):

```sql
select
  (select count(*) from public.payment_methods)  as formas_de_pagamento,
  (select count(*) from public.banks)            as bancos,
  (select count(*) from public.item_categories)  as categorias,
  (select count(*) from public.clients)          as pessoas,     -- tem de ser 0
  (select count(*) from public.sales)            as vendas,      -- tem de ser 0
  (select count(*) from public.donations_cash)   as doacoes,     -- tem de ser 0
  (select count(*) from auth.users)              as contas;      -- 0 até o passo 5
```

## 5. Auth e contas de conferência

O `db push` não leva as configurações do Auth nem as contas. No painel do projeto novo:

1. **Configurações do Auth:** copie do projeto atual, tela por tela, o que estiver diferente do padrão: cadastro aberto ou fechado (o sistema não tem tela de cadastro; o esperado é fechado), Site URL e Redirect URLs, modelos de e-mail se tiverem sido mudados. Anote no `PROGRESSO.md` cada ajuste.
2. **Contas de conferência da equipe**, uma por perfil (coordenação, voluntária, caixa), criadas em Authentication, Users, Add user, com e-mail confirmado. Senhas no gerenciador de senhas.
3. **Perfil de cada conta** em `public.users`, no SQL Editor, como no `supabase/seed-user.sql` (é cadastro de dado, e não mudança de esquema; até a US-24 trazer a tela, é assim):

   ```sql
   insert into public.users (id, name, role)
   select id, 'Conferência · Coordenação', 'admin' from auth.users where email = '<e-mail da conta>'
   on conflict (id) do update set name = excluded.name, role = excluded.role, active = true;
   ```

   Repita com `'volunteer'` e `'cashier'` para as outras duas.

As contas do Instituto (Flávia, Ana, Nílian, Tamara) só são criadas na virada, depois de a revisão de 30/10 dizer quem continua usando o sistema.

## Regra das migrações

Migração em produção só por `supabase db push`, com o CLI ligado ao projeto de produção, depois do merge na `main`. Nunca pelo SQL Editor. Antes e depois, `supabase migration list`; a saída vai para o `PROGRESSO.md` da sprint. O SQL Editor fica para leitura e para o cadastro de perfis até a US-24.

Ordem numa story com migração: PR aprovado, `db push` no banco de produção, merge, conferência na tela.

## Roteiro da virada

1. Aviso no grupo do Instituto, uma hora antes, depois das 22h.
2. `migration list` no projeto novo sem pendência.
3. Contas do Instituto criadas no Auth do projeto novo, com o perfil em `public.users`.
4. Na Vercel, Production: `NEXT_PUBLIC_SUPABASE_URL` e `NEXT_PUBLIC_SUPABASE_ANON_KEY` do projeto novo. Novo deploy de produção.
5. Conferência: login dos três perfis, uma venda e uma doação de verdade (ou de teste, apagada em seguida pela coordenação), relatório.
6. Volta, se algo der errado: repor as duas variáveis antigas e fazer novo deploy. O banco antigo não muda na virada.
7. Preview passa a apontar para o banco antigo (que já é o que ele usa hoje).
